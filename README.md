# AI-Powered Hotel Guest Check-In Assistant

MSc Project in Computer Science — Candidate 0413976, Supervisor Dr Paul Sant

A self-service hotel check-in system: guests scan their passport/ID (OCR),
verify their identity with a live selfie (face matching), get matched
against their booking automatically, and are guided through the process by
an AI voice assistant.

---

## 1. Tech stack

| Layer | Technology |
|---|---|
| Frontend | Next.js 14 (App Router) + TypeScript + Tailwind CSS |
| Backend | Python FastAPI |
| OCR | Tesseract (via `pytesseract`) |
| Face verification | DeepFace |
| Voice assistant | Ultravox API (WebSocket bridge) |
| Database | PostgreSQL 16 |
| Containerisation | Docker + Docker Compose |

---

## 2. Prerequisites

Install these once on your machine:

1. **Docker Desktop** — https://www.docker.com/products/docker-desktop/
   (make sure it's running before you start the stack)
2. **VS Code** — https://code.visualstudio.com/
3. **Git** (to clone/version the project)

You do **not** need Python or Node.js installed locally — everything runs
inside Docker containers. (Optional: install them locally too if you want
to run tests outside Docker, or use the VS Code Dev Containers workflow
described below.)

## 3. First-time setup

### 3.1 Get the project into VS Code

```bash
cd hotel-checkin-assistant
code .
```

When VS Code opens, it will prompt you to install the recommended
extensions listed in `.vscode/extensions.json` (Python, Docker, ESLint,
Prettier, Tailwind CSS IntelliSense, PostgreSQL, GitLens). Click **Install
All**.

### 3.2 Configure environment variables

```bash
# Root — used by docker-compose.yml for the Postgres password
cp .env.example .env

# Backend — API keys, DB URL, thresholds
cp backend/.env.example backend/.env

# Frontend — points the browser at the backend API
cp frontend/.env.local.example frontend/.env.local
```

Open `backend/.env` and fill in:
```
ULTRAVOX_API_KEY=<your real Ultravox API key>
```
Everything else has sensible local-dev defaults — you can leave them as-is
to start.

### 3.3 Build and start everything

With **Docker Desktop running**, from the project root:

```bash
docker compose up --build
```

This builds and starts three containers:
- `checkin-db` — PostgreSQL, seeded with sample bookings from `database/init.sql`
- `checkin-api` — FastAPI backend on **http://localhost:8000**
- `checkin-web` — Next.js frontend on **http://localhost:3000**

`docker-compose.override.yml` is picked up automatically alongside
`docker-compose.yml`, giving you hot-reload for both frontend and backend
while developing, plus a `pgAdmin` container on **http://localhost:5050**
(login: `admin@example.com` / `admin`) for inspecting the database visually.

First build takes a few minutes (installing Tesseract, DeepFace's model
dependencies, and npm packages). Subsequent runs are much faster.

### 3.4 Verify it's working

- Backend health check: open **http://localhost:8000/api/v1/health** →
  should return `{"status": "ok", ...}`
- Interactive API docs (auto-generated by FastAPI): **http://localhost:8000/docs**
- Frontend: **http://localhost:3000** → should show the "Start Check-In" screen

You can also check container status directly in the **Docker Desktop**
app under the "Containers" tab — all three (`checkin-db`, `checkin-api`,
`checkin-web`) should show a green/running status. This view is worth a
screenshot for your report's Implementation chapter.

## 4. Everyday commands

```bash
docker compose up -d          # start in background
docker compose logs -f api    # tail backend logs
docker compose logs -f web    # tail frontend logs
docker compose down           # stop everything (keeps DB data)
docker compose down -v        # stop AND wipe the database volume (fresh start)
docker compose restart api    # restart just the backend after a dependency change
```

## 5. Developing in VS Code

### Option A — edit locally, run in Docker (simplest)
Just edit files in `backend/app/` or `frontend/`. Because the dev override
mounts these folders into the running containers with `--reload` / `npm run
dev`, changes appear live without rebuilding.

### Option B — Dev Containers (recommended for backend debugging)
1. Install the **Dev Containers** extension (already in the recommended list)
2. `Ctrl/Cmd+Shift+P` → **Dev Containers: Attach to Running Container** →
   select `checkin-api`
3. VS Code reopens *inside* the container — you get the exact Python
   environment (Tesseract, DeepFace, all pinned dependencies) with no
   local install needed, and can set breakpoints normally.

### Debugging (F5)
`.vscode/launch.json` includes two ready-made configs:
- **FastAPI: Debug** — runs the backend directly under the debugger
  (requires `pip install -r backend/requirements.txt` in a local venv, or
  use it from inside a Dev Container attach session)
- **Pytest: Backend tests** — runs the unit tests with breakpoints enabled

### Running backend tests
Inside the `api` container (or a local venv with requirements installed):
```bash
docker compose exec api pytest app/tests -v
```

## 7. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| `docker compose up` fails on `db` | Port 5432 already in use locally — stop any local Postgres, or change the host port mapping in `docker-compose.yml` |
| Backend can't reach DB | Wait a few seconds — `api` waits on `db`'s healthcheck, but first-run image pulls can be slow. Check `docker compose logs db` |
| Camera / microphone don't work in the browser | WebRTC requires HTTPS or `localhost` — this setup uses `localhost:3000`, which browsers treat as a secure origin, so this should work locally out of the box |
| No webcam available | The scan and verify pages now include an **"Upload Photo Instead"** button next to the live-capture button — it appears automatically if no camera is detected/permitted, and is always available otherwise. Use it to upload sample ID/face images from disk instead of a live capture. Voice/microphone has no equivalent fallback in the UI; test that via the backend WebSocket directly if you have no mic (see Section 8 of the previous design notes). |
| DeepFace build is slow / fails | Its first run downloads pretrained model weights — ensure Docker Desktop has internet access and enough allocated memory (Settings → Resources, 4GB+ recommended) |
| Changes to `requirements.txt` / `package.json` not picked up | Rebuild that service: `docker compose up --build api` (or `web`) |

## 8. Known limitations (be upfront about these in your report)

- **OCR extraction is a heuristic stub**, not a production pipeline — `_guess_name`/`_guess_dob`/`_guess_document_number` use crude regex/MRZ-line matching that works on MRZ-formatted documents but will miss fields on many real-world ID layouts. `confidence` is currently hardcoded and not a real accuracy score — you'll need to build actual measurement against a labelled test set for the evaluation chapter.
- **No bias/fairness evaluation exists yet** for face verification, despite the proposal mentioning it — that requires a demographically varied test set and analysis you'll need to design and run yourself.
- **The 0.40 face-match threshold is an unvalidated default**, not tuned against real data — your performance-evaluation deliverable needs a real false-accept/false-reject analysis to justify (or change) this number.
- **No Alembic migrations are set up** — only `database/init.sql`. If your report or demo needs to show schema evolution, you'll need to `alembic init` and generate a first revision from the current models.
- **Security defaults are dev-grade** (`SECRET_KEY`, DB password) — fine for a Docker dev stack, but call this out explicitly if your report claims GDPR-aligned practices; production would need real secret management.
- **The OCR → Guest → reservation → check-in flow is now wired end-to-end**: `/api/v1/reservation/match` persists a `Guest` row on a successful match and returns its `guest_id`, which the frontend passes to `/api/v1/checkin/complete`. This closes the gap that previously left each endpoint working only in isolation.
- **Re-check-in is now blocked**: a booking's `status` flips to `CHECKED_IN` when `/checkin/complete` succeeds, and `MatchingService` refuses to match against a booking already in that state (returns a clear "already checked in" reason instead of silently allowing it again). Repeated matching attempts before completion also now reuse the same `Guest` row rather than creating duplicates.

If you were testing before this fix, your `guests` table may still contain duplicate rows from repeated retries (visible via pgAdmin's Query Tool). Safe to clear out for a fresh demo:
```sql
DELETE FROM verification_logs;
DELETE FROM guests;
UPDATE bookings SET status = 'CONFIRMED';  -- reset any bookings you'd marked CHECKED_IN while testing
```
